## 0. Executive summary

- Keep the 2026-09-02 spec's core: a `variables:` list, `"main"` as the
  normalized name of a legacy single-variable codebook, one `extractions`
  row per (document, variable), `per_variable` as the default prompt
  strategy with `joint` as an opt-in, neutral field names
  `category`/`rationale`/`evidence_span`, the startup column rename inside
  `db.py`, and per-variable validation calls.
- Add `multi_label: true` as a **per-variable** flag (default `false`), with
  optional `min_labels` (default `0`) and `max_labels` (default unbounded).
  The empty set is the representation of "none of the above"; no implicit
  `none` category is generated.
- A multi-label variable's output is a list of **selections**, each with its
  own `label`, `rationale`, and `evidence_span`, plus one set-level
  `rationale`. Per-label evidence is what keeps each label auditable; the
  set-level rationale is where the model explains what it did *not* pick,
  which is the review surface for over-coding.
- Storage stays one row per (document, variable). Multi-label rows carry the
  selections as a JSON column (`selections_json`); single-label rows keep the
  flat `category`/`rationale`/`evidence_span` columns. Gold labels mirror this
  (`labels_json`) so the existing "more than one gold row = multiple coders"
  rule keeps working per variable.
- Gold CSV: one `gold_<variable>` column per variable; multi-label cells use
  `|` as the delimiter and the literal token `[]` for a reviewed empty set.
  `;` is rejected because pt-BR Excel writes CSV with `;` as the field
  separator.
- Validation for multi-label variables ships two metric families in R1.1:
  per-label binary (kappa, P/R/F1, false-positive rate, predicted vs gold
  counts) and set-level (exact-match ratio, sample-averaged Jaccard, mean
  predicted vs gold set size, over-/under-coded document counts). Krippendorff's
  alpha with MASI distance and Gwet's AC1 are deferred to R6.1, which becomes
  additive: the report shape already has the slots.
- The Mercês et al. (SBES 2026) "Excessive Granularity Bias" finding is
  addressed three ways: the over-coding signals above are on the Validation
  screen from day one; the multi-label prompt carries a neutral parsimony
  sentence plus the `min_labels`/`max_labels` bounds when set; and
  `per_variable` stays the default so each call's label space is as small as
  the codebook allows.
- Portuguese identifiers disappear from Python and TypeScript in one
  mechanical commit (step 1 of §10); the pt-BR UI copy stays where it already
  lives, `frontend/src/locales/pt-BR.json`.

## 2. YAML shape

### 2.1 Today's single-variable file, unchanged and still valid

```yaml
concept: protest
description: >
  A collective, public event expressing a political or social claim,
  involving at least two people.
categories:
  - label: protest
    definition: ...
  - label: not_protest
    definition: ...
```

Normalizes internally to `variables: [{name: main, description: <same as top-level>, multi_label: false, categories: [...]}]`.
The three DATALUTA pilot codebooks (`decifra-dataluta-pilot/codebooks/codebook_ods*.yaml`)
and every YAML in `tests/fixtures` load without edits.

### 2.2 Two-variable codebook: one single-label, one multi-label

A protest-coverage codebook where each article gets exactly one event type
and any number of UN Sustainable Development Goals — the DATALUTA group's
actual scheme, whose gold data has a mean of 2.5 of 17 labels per item and
only 24% single-label documents (`TODO.md`, 2026-09-09).

```yaml
concept: land_conflict_coverage
description: >
  News coverage of agrarian, socio-environmental and traditional-peoples
  conflicts in Brazil. Each article is coded for the type of event it
  reports and for the UN Sustainable Development Goals it bears on.

prompt_strategy: per_variable   # default; "joint" = one call per document (§4)

variables:
  - name: event_type            # snake_case identifier; becomes a dataset column
    description: >
      The main event the article reports. Exactly one applies.
    # multi_label: false        # default; may be omitted
    categories:
      - label: protest
        definition: >
          An occupation, march, blockade or public act with a declared
          demand directed at an authority or company.
        positive_examples:
          - "BR-262 em Taunay é palco de manifestação indígena contra o marco temporal"
        negative_examples:
          - "Malungu define ações para os próximos dois anos, com o apoio da Ecam"
        boundary_notes: >
          A meeting or assembly with no demand aimed outward is not a protest.
      - label: violence
        definition: >
          An attack, threat, killing or forced eviction against a community
          or its leaders, reported as the article's central event.
      - label: institutional_act
        definition: >
          A court ruling, agency decision, bill or hearing is the central
          event; no protest or violence is the main story.
      - label: other
        definition: "Any article that fits none of the above."

  - name: sdg_goals
    description: >
      Every UN Sustainable Development Goal the article's central conflict
      bears on. Select all that apply; most articles carry two or three.
    multi_label: true           # output is a SET of labels, possibly empty
    min_labels: 0               # default; 0 means the empty set is a valid answer
    max_labels: 5               # optional; omitted = no upper bound. Enforced in
                                # the output schema AND stated in the prompt (§4.2)
    categories:
      - label: sdg_5_gender_equality
        definition: >
          Gender-based violence, women's leadership or women's collective
          organizing is part of the conflict as narrated.
        positive_examples:
          - "Kuñangue Aty Guasu reúne mulheres Guarani e Kaiowá contra a violência"
        negative_examples:
          - "Lideranças indígenas pedem exoneração do presidente da Funai"
        boundary_notes: >
          The mere presence of a woman in the story is not enough; gender
          must be part of the claim, the harm, or the organization.
      - label: sdg_15_life_on_land
        definition: >
          Deforestation, biome degradation, land titling or territorial
          protection is part of the conflict.
      - label: sdg_16_peace_justice
        definition: >
          The state, courts, legislation or international bodies are the
          arena of the conflict, or defenders of rights suffer violence.
        boundary_notes: >
          The state appearing only as a service provider (food baskets,
          health care) does not count.
      # ... the remaining SDGs follow the same shape (17 in the real scheme)
```

### 2.3 Validation rules (`validate_spec`, `codebook.py:27-72`)

Rules kept from 2026-09-02: `concept` and `description` required; exactly
one of top-level `categories` / `variables`; variable `name` matches
`^[a-zA-Z_][a-zA-Z0-9_]*$`, unique; each variable's `categories` validated
with today's per-category logic (label a non-empty string, `definition`
required, labels unique within the variable); `prompt_strategy` in
`{per_variable, joint}`.

New rules:

- `multi_label` is optional, must be a boolean, defaults to `false`.
- `min_labels` and `max_labels` are only allowed when `multi_label: true`
  (rejected otherwise — a silent no-op would be a codebook-authoring bug).
  Both must be non-negative integers; `min_labels <= max_labels`;
  `max_labels <= len(categories)`; `min_labels` defaults to `0`,
  `max_labels` defaults to `None` (unbounded).
- For a multi-label variable, every label must be free of the gold-CSV
  delimiter `|`, must not have leading/trailing whitespace, and must not be
  the literal `[]` (the reviewed-empty-set token, §7). Single-label variables
  are not constrained this way; they never round-trip through a delimited
  cell.
- Reserved variable names: `main` is reserved for the shorthand and may not
  be declared explicitly. The rest of the reserved set is derived from the
  export and results column namespace: `{id, run_id, document_id,
  document_snippet, category, categories, rationale, evidence_span,
  variable, tokens_used, prompt_sent, raw_response}`. In addition, the
  derived export columns of all variables (`<name>`, `<name>_rationale`,
  `<name>_evidence_span`, `<name>_selections`) must be pairwise distinct —
  so `x` and `x_rationale` cannot coexist as variable names. Checked once in
  `validate_spec`, not scattered across exporters.
- A variable's `description` is required (it is the question the LLM is
  asked; for the shorthand it is copied from the top-level `description`).

### 2.4 Why the empty set, not an implicit `none` category

Recommendation: **the empty list is the representation of "none of the
above"; the engine does not synthesize a `none` label.** A codebook author
who wants an affirmative "none" may still declare one as an ordinary
category, and the engine will not special-case it.

Justification. An engine-generated `none` label would need an exclusivity
rule (`none` cannot co-occur with anything), which is a second kind of
constraint to validate, prompt for, and explain in the UI; it would also
appear in the per-label metric table as a label whose binary kappa is just
the complement of "any label present", diluting the table. The empty set
needs none of that: the schema is `list[...]` with `min_length=min_labels`,
the prompt says "return an empty list if no category applies", set metrics
handle it with one convention (Jaccard(∅, ∅) = 1), and the gold CSV has one
explicit token for it. The cost is that a model reluctant to return an
empty list will over-code instead — which is exactly the bias §8.4 makes
measurable, so the researcher sees it rather than having it hidden behind a
`none` label the model was equally free to skip.

## 3. Output schema per variable

All names in English, as `AGENTS.md`'s codebook-format section already
uses. Built with `create_model` as today (`codebook.py:151-159`), once per
variable.

### 3.1 Single-label (`multi_label: false`)

```python
create_model(
    f"{Name}Extraction",
    category=(Literal[tuple(labels)], Field(description="Exactly one of the codebook's category labels.")),
    rationale=(str, Field(description="Free-text rationale for the chosen category.")),
    evidence_span=(str, Field(description="Verbatim quote from the document that grounds the decision.")),
)
```

Identical to today except for the three names.

### 3.2 Multi-label (`multi_label: true`)

```python
Selection = create_model(
    f"{Name}Selection",
    label=(Literal[tuple(labels)], Field(description="One selected category label.")),
    rationale=(str, Field(description="Why this label applies to this document.")),
    evidence_span=(str, Field(description="Verbatim quote from the document that grounds THIS label.")),
)
create_model(
    f"{Name}Extraction",
    selections=(
        list[Selection],
        Field(min_length=min_labels, max_length=max_labels,   # max_length omitted when None
              description="Every category whose definition is met, and only those. Empty if none applies."),
    ),
    rationale=(str, Field(description=(
        "Overall reasoning for the set as a whole, including which near-miss "
        "categories were considered and why they were not selected."))),
)
```

Duplicate labels inside `selections` are deduplicated (first occurrence
wins) in `extraction.py` after parsing rather than rejected by a validator:
a duplicate is not a wrong answer, and rejecting it would burn a retry in
CLI mode for nothing. The raw response is stored untouched either way.

### 3.3 Why one `rationale`/`evidence_span` **per selected label**, plus one set-level `rationale`

Recommendation: per-label, not per-set.

Justification. `AGENTS.md` says the `evidence_span` "is what makes the
decision auditable later". In a multi-label variable the researcher's unit
of review is a single label on a single document — "why did the model say
this article bears on SDG 5?" — not the set. One quote for a set of three
labels cannot ground each of them, and `verify_evidence_span()`
(`extraction.py:28-60`) could not tell which label the quote supports. The
DATALUTA pilot's dossier of 53 disagreements (`decifra-dataluta-pilot/README.md`)
was only possible because each binary codebook produced its own quote; the
multi-label design must not lose that. The set-level `rationale` is kept
because the empty set otherwise has nowhere to explain itself, and because
the SBES over-coding finding makes "what did you consider and reject" the
most useful review text for a multi-label variable. Output-token cost grows
roughly with mean set size (2.5× for the SDG scheme); `estimate.py` must
account for it (§10 step 3).

## 4. Prompt strategy and cache key

### 4.1 Decision: keep `per_variable` as the default, `joint` as opt-in

Multi-label does not reopen this. The `TODO.md` item's concern — the pilot's
N one-vs-rest binary codebooks "lose any joint reasoning across labels" — is
about reasoning across the labels *of one scheme*; declaring the scheme as a
single `multi_label` variable restores that reasoning in a single call
regardless of `prompt_strategy`. The remaining question is only whether
*different* variables share a call, and here the SBES finding tips the scale
towards `per_variable`: Mercês et al. found LLM over-assignment scaling with
codebook size (~28% at 6 codes, ~57% at 15 codes; `docs/research/2026-09-08_sbes_deductive_coding_and_annotaise_comparison.md` §2.2).
Concatenating a 17-label variable with others into one prompt is the
largest label space the tool can present; `per_variable` presents the
smallest. `joint` remains available for the case the 2026-09-02 spec argued
(long documents, many cheap variables, token cost dominant), and the author
should not choose it for a codebook containing a large multi-label variable
without measuring.

### 4.2 The multi-label prompt

The per-variable instructions block is today's `codebook.py:161-170` text
with the variable's `description` in place of the codebook-level one
(preceded by the codebook-level `concept`/`description` as a one-paragraph
preamble, so the variable is asked in context). For a multi-label variable
the block ends with a fixed, engine-owned paragraph:

> Select every category whose definition is met, and only those. Do not add
> a category because the document is loosely related to it; a category
> applies only when its definition is satisfied. Quote the specific passage
> that grounds each selected category. If no category applies, return an
> empty list and explain why in the overall rationale.
> *(when `min_labels > 0`)* Select at least N categories.
> *(when `max_labels` is set)* Select at most N categories.

Two things this paragraph deliberately does **not** do: it does not inject a
numeric prior about typical set size (that is gold-distribution knowledge
that would bias a prevalence estimate — a researcher who wants it can put it
in the variable's `description`, as the §2.2 example does), and it does not
change how `positive_examples` are injected. Mercês et al. found one-shot
beat few-shot on their task (examples overfit the surface form); that is a
separate, testable run-parameter question the SBES doc already records
(§4.2 item 3) and R1.1 does not pre-empt it.

`max_labels` is therefore both a schema constraint (instructor re-asks on
violation in API mode; CLI mode retries then errors) and a prompt sentence.
The two together are the mitigation lever for over-coding; the default is
unbounded so a codebook that does not want the constraint is not silently
given one.

### 4.3 Cache keys

- **`per_variable`**: a cache hit is the most recent `ExtractionRecord` with
  the same `document_id`, `variable`, `variable_spec_hash`, and — via the
  join on `RunRecord` — the same `model` and `provider_mode`, with
  `original_result_json == ""` (never reuse a human-edited row) and
  `category != "__error__"`. The last three filters are in the live code
  (`extraction.py:174-176`) and were dropped from the 2026-09-02 sketch; they
  stay. `.first()` remains correct because a (document, variable) pair has
  at most one row per run.
- **`variable_spec_hash`** = `sha256(canonical_json({"template": PROMPT_TEMPLATE_VERSION, "concept": ..., "description": ..., "variable": <normalized variable spec>}))`
  where the normalized variable spec includes `name`, `description`,
  `multi_label`, `min_labels`, `max_labels`, and the full `categories` list
  with defaults filled in. Including the codebook-level `concept`/`description`
  is required because they are in the prompt (§4.2). `PROMPT_TEMPLATE_VERSION`
  is a new integer constant in `codebook.py`, bumped whenever the fixed
  instruction text (persona, the parsimony paragraph, the list formatting)
  changes — today a change to `_PERSONA` (`codebook.py:105-110`) does not
  invalidate any cache, which is a pre-existing gap this closes at no cost.
  Because the hash is over the *normalized* spec, re-saving a shorthand
  codebook from the editor in explicit `variables:` form does not invalidate
  the cache.
- **`joint`**: as in 2026-09-02 — `(document, RunRecord.codebook_id, codebook_yaml_hash, model, provider_mode)`, `.all()`, every declared variable must be present. `codebook_yaml_hash` should also become a hash of the normalized spec rather than of the raw text, for the same reformatting reason; this also fixes `app.py:556`, where the reproducibility endpoint would reject two runs of a codebook that was merely re-saved. Name kept, semantics changed; legacy rows are handled in §5.4.

## 5. Storage

### 5.1 Decision: one row per (document, variable); multi-label sets as a JSON column on that row

Recommendation over the two alternatives the brief names (one row per
document with a JSON column per variable; one row per selected label).

Justification. Filtering, validation and export at R1.1 scale all happen in
Python on a run's full row set (`get_run_results` returns every row,
`ResultsTable.tsx:57` filters client-side; validation builds DataFrames in
`app.py`; export pivots in `app.py`). None of them benefits from a
relational per-label table, and a per-label ("long") layout would break
three things that work today: the cache lookup's `.first()` (would need the
joint-mode `.all()`-and-verify logic for every multi-label variable), the
per-row `PUT /runs/{id}/results/{extraction_id}` (editing a set would mean
inserting/deleting rows), and the gold-label rule "more than one row per
document means multiple coders" (`app.py:439-443`), which would misread a
three-label gold set as three coders. A JSON-per-variable row on a single
per-document row has the same problems the 2026-09-02 spec listed against
it (per-variable `prompt_sent`/`raw_response` become impossible, every
per-row operation parses a blob). If server-side per-label filtering is ever
needed (R5.2 pagination), SQLite's `json_each` works on the column as
stored; a child table is the escape hatch then, not now.

### 5.2 `ExtractionRecord` (`db.py:102-131`)

    document_id: int = Field(foreign_key="documents.id")
    variable: str = "main"            # NEW. Codebook variable this row answers.
    variable_spec_hash: str = ""      # NEW. §4.3; "" for joint-mode rows and legacy rows.
    category: str                     # RENAMED from categoria. Single-label: the label.
                                      #   Multi-label: "" (see selections_json).
                                      #   Either: "__error__" on failure.
    rationale: str                    # RENAMED from justificativa. Single-label: rationale.
                                      #   Multi-label: the set-level rationale. Error: the message.
    evidence_span: str                # RENAMED from trecho_evidencia. Multi-label: "".

### 5.4 Migration of the author's own database

All automatic at `get_engine()` (`db.py:193-219`), in this order:

1. `_apply_legacy_renames` (the 2026-09-02 design, unchanged): `ALTER TABLE
   extractions RENAME COLUMN categoria TO category` etc., guarded by
   "old exists and new does not", before `_ensure_columns`.
2. `_ensure_columns` adds `variable` (`DEFAULT 'main'`), `variable_spec_hash`,
   `selections_json` on `extractions` and `variable`, `labels_json` on
   `human_labels`. `_ensure_columns` already emits `DEFAULT` for scalar
   Python defaults (`db.py:188-190`), so every legacy row reads back as a
   `"main"` single-label row with no further work.
3. **Optional one-shot backfill** (author decision §11.6; default: do it):
   legacy `extractions` rows have `variable_spec_hash = ""` and would never
   be cache hits again under the per-variable key, so every already-paid
   extraction (the DATALUTA pilot alone has 243 CLI calls in
   `resultados/pilot.sqlite`) becomes unreachable. A guarded backfill
   recomputes the hash for each legacy row whose run's `codebook_yaml_hash`
   still equals `sha256(current CodebookRecord.yaml_raw)` — i.e. the codebook
   has not been edited since — and leaves any other row alone. Roughly
   thirty lines, in `db.py` next to the renames, idempotent (skips rows with
   a non-empty hash). Rows it cannot prove are current are simply not reused.

A brand-new database never has `categoria`, so steps 1 and 3 are no-ops.
Tests: the fixture-file test the 2026-09-02 spec already specified
(`tests/test_db_migration.py` style, `tests/test_db_migration.py:19-40`),
plus one asserting a legacy row is served as a cache hit after backfill and
one asserting an edited-codebook legacy row is not.

## 7. Gold labels

### 7.1 CSV convention

One `gold_<variable>` column per declared variable; each independently
optional per row; blank = not yet reviewed for that variable (as today,
`app.py:357-360`). The upload needs `document_id` plus at least one
`gold_<variable>` column whose name matches a declared variable; a
`gold_...` column matching no variable is a 422 (a typo in a variable name
must not silently drop a whole column of human work). `gold_categoria`
disappears with the rename; for a shorthand codebook the column is
`gold_main`, and the upload accepts `gold_category` as an alias for it so
the single-variable workflow reads naturally in the UI copy.

### 7.2 Multi-label cells

- Delimiter: **`|`**. Labels are split on `|`, each token stripped. Commas
  are rejected as a delimiter because they force quoting in CSV and confuse
  spreadsheet users; `;` is rejected because Excel with a pt-BR locale
  (the author's and the DATALUTA group's) writes CSV with `;` as the *field*
  separator, so a `;`-delimited cell would be split into columns on the next
  round trip.
- Reviewed empty set: the literal token **`[]`**. Blank still means "not
  reviewed". `none` was considered and rejected because it is a plausible
  real label (the DATALUTA codebooks use `ausente`).
- Ambiguity handling in the parser: a label containing `|` cannot exist
  (rejected at codebook validation, §2.3), so a cell can always be split
  unambiguously. An empty token (`a||b`, `|a`, `a|`) is a 422 naming the
  row. An unknown label is a 422 naming the row, as today
  (`app.py:361-363`). Duplicate tokens (`a|a`) are deduplicated and counted
  in the response (`"deduplicated": n`), not rejected — a duplicate is not a
  typo. All-or-nothing on validity stays (`app.py:371-375`).
- A `|` in a *single-label* gold cell is just an invalid label and gets the
  existing unknown-label 422.

The DATALUTA gold source is one-hot (`ods_5,ods_15,ods_16` columns,
`decifra-dataluta-pilot/dados/gold_dataluta_val.csv`). Accepting indicator
columns (`gold_sdg_goals.sdg_5_gender_equality = 0/1`) as an alternate form
is a small parser but a second convention to document and test; recommended
default is not to ship it in R1.1 and to document the one-line pandas
conversion instead (author decision §11.3).

### 7.3 Storage and the delete query

One `HumanLabelRecord` per (document, variable, non-blank cell); multi-label
sets in `labels_json`, sorted. The replace-before-insert delete
(`app.py:382-388`, and the QualiLab path at `app.py:838-844`) is scoped to
`HumanLabelRecord.variable == variable` — the 2026-09-02 data-loss fix,
unchanged.

## 8. Validation metrics

### 8.1 Single-label variables

Unchanged: `agreement_report()` (`validation.py:9-85`) is called once per
variable on narrow, gold-filtered frames, as the 2026-09-02 spec corrected
(no wide pivot; no `NaN` in the label sort at `validation.py:54`). Report
shape per variable is today's `{coverage, per_category, disagreements}`.

### 8.2 Multi-label variables: a new `multilabel_agreement_report()` in `validation.py`

Signature mirrors `agreement_report`: two DataFrames with `id_col` and one
column holding `frozenset[str]`, plus the variable's full label list (so a
label that never occurs still gets a row of zeros rather than vanishing).
Same one-gold-row-per-id guard (`validation.py:24-39`).

**Per-label binary family** (ships in R1.1). For each label L, build the
indicator vectors `pred_has_L`, `gold_has_L` and report: `kappa`
(`cohen_kappa_score`, `None` when undefined, as today at
`validation.py:59-66`), `precision`, `recall`, `f1` (positive class =
present), `false_positive_rate` = FP/(FP+TN), `predicted_count`,
`gold_count`. This is the decomposition every published multi-label
evaluation uses and it is what the pilot already computed by hand with N
binary codebooks — so the multi-label report is directly comparable to the
pilot's ODS 5/15 numbers.

**Set-level family** (ships in R1.1):

| Measure | Definition | Ship? | Why |
|---|---|---|---|
| `exact_match_ratio` | share of documents with pred == gold | **Yes** | Strictest; directly comparable to Mercês et al.'s "Full Agreement" (40.6% → 11.8% → 10.4% as codebook size grew), so the SBES scaling law can be checked against Decifra's own output. |
| `mean_jaccard` | mean over documents of \|∩\|/\|∪\|, with J(∅, ∅) = 1 | **Yes** | The standard partial-credit set measure; one number the researcher can quote for "how close". |
| Hamming-based agreement | 1 − (\|Δ\| / \|labels\|) averaged | **No** | With 17 labels and mean set size 2.5 it is dominated by true negatives and reads ~0.9 for a poor coder — the same failure accuracy has under imbalance, and the reason kappa exists. Not worth a misleading number on the screen. |
| Krippendorff's alpha with MASI distance | chance-corrected set agreement | **Defer to R6.1** | R6.1 is the chance-corrected-agreement brief (alpha, Gwet's AC1) and says "test against published worked examples"; MASI-alpha belongs there with that discipline. The report shape below leaves it a slot. |

**Over-/under-coding signals** (ships in R1.1; requested to make the SBES
"Excessive Granularity Bias" measurable from day one): `mean_predicted_set_size`,
`mean_gold_set_size`, `set_size_ratio` (predicted/gold), and a document-level
breakdown into `exact` (pred == gold), `over_coded` (pred ⊋ gold — Mercês et
al.'s "Equivalent Coding with Expansion" as a mechanical proxy),
`under_coded` (pred ⊊ gold), `mixed` (neither a subset of the other). The
per-label `false_positive_rate` and `predicted_count`/`gold_count` above
show *which* labels absorb the over-coding. Together these let the author
run the SBES doc's own recommendation ("measure this ... before shipping
multi-label, not after") on the DATALUTA corpus as the first real use of
the feature.

**Report shape** per multi-label variable:

```json
{
  "coverage": {"labeled": 141, "total": 141, "excluded_multi_coder": 0},
  "kind": "multi_label",
  "per_label": {
    "sdg_5_gender_equality": {"kappa": 0.45, "precision": 0.36, "recall": 0.80, "f1": 0.50,
                              "false_positive_rate": 0.11, "predicted_count": 22, "gold_count": 10}
  },
  "set_agreement": {"exact_match_ratio": 0.41, "mean_jaccard": 0.66,
                    "mean_predicted_set_size": 3.1, "mean_gold_set_size": 2.5, "set_size_ratio": 1.24,
                    "documents": {"exact": 58, "over_coded": 49, "under_coded": 20, "mixed": 14}},
  "disagreements": [ ... ]
}
```

Single-label variables report `"kind": "single_label"` with today's
`per_category` block. R6.1 adds `krippendorff_alpha`/`gwet_ac1` keys inside
`per_label[*]` and `set_agreement` (and inside `per_category` for
single-label) without moving anything. R6.6's PPI prevalence estimate needs
exactly the per-label indicator vectors this function builds; expose them
via a small helper so R6.6 does not rebuild them. R6.8's codebook-version
check attaches to `HumanLabelRecord` per variable; `variable_spec_hash` is
the natural key for "was this gold set coded against the current version of
*this* variable", finer than the whole-codebook hash R6.8 proposes.

### 8.3 What a disagreement row is for a multi-label variable

Any document where pred ≠ gold as sets. Each row carries `document_id`,
`document_snippet`, `predicted: [...]`, `gold: [...]`, `only_predicted: [...]`,
`only_gold: [...]`, and for every label in `only_predicted` that label's own
`rationale` and `evidence_span` from `selections_json` — the payoff of §3.3:
an over-coded label is reviewable on the spot. Rows are sorted by
`|only_predicted| + |only_gold|` descending. The single-label disagreement
row (`app.py:474-486`) is unchanged.

### 8.4 Reproducibility (`app.py:531-577`)

Per variable, as in 2026-09-02; for a multi-label variable it calls
`multilabel_agreement_report()` with run B in the gold position and relabels
keys the way `reproducibility_report()` does today (`validation.py:106-112`).
`exact_match_ratio` and `mean_jaccard` are the self-agreement numbers.

## 11. Decisions reserved for the author (recommended default in bold)

1. **Empty set as "none of the above"** vs an engine-generated exclusive
   `none` category. Default: **empty set** (§2.4). A codebook may still
   declare its own `none`-like label as an ordinary category.
2. **Per-label `rationale`/`evidence_span` plus one set-level `rationale`**
   vs one rationale/quote per set. Default: **per-label + set-level** (§3.3).
   The cost is output tokens roughly proportional to set size.
3. Gold CSV syntax: **`|` delimiter, `[]` for a reviewed empty set, no
   one-hot indicator columns in R1.1** (§7). Alternative: also accept
   `gold_<variable>.<label> = 0/1` columns because that is how the DATALUTA
   gold arrives.
4. Multi-label metric set for R1.1: **per-label kappa/P/R/F1/FPR/counts +
   exact-match + Jaccard + set-size and over/under-coding counts; MASI-alpha
   and Gwet deferred to R6.1** (§8.2). Alternative: pull MASI-alpha forward
   into R1.1 (adds a dependency or a hand-rolled alpha that R6.1 would then
   have to validate against published examples anyway).
5. **Keep `prompt_strategy: joint` in R1.1 as the last backend step** (§10
   step 8) vs move it to a new R1.2 brief so R1.1 ships sooner. Default:
   keep, last — it was an explicit author request on 2026-09-02, and it is
   the natural replacement for `pilot_v7.py`'s hand-rolled pair builder.
6. **Backfill `variable_spec_hash` for legacy rows whose codebook is
   unchanged** (§5.4) vs accept a one-time re-bill of every cached
   extraction. Default: backfill.

Everything else in this document is a recommendation the author is asked to
accept as a block or annotate inline.

## 13. Risks, and things the earlier documents got wrong or could not know

1. **Excessive Granularity Bias lands on this feature directly.** Mercês et
   al. (SBES 2026) measured LLM over-assignment rising from ~28% at 6 codes
   to ~57% at 15 and 28 codes, with exact agreement collapsing from ~41% to
   ~12% (`docs/research/2026-09-08_sbes_deductive_coding_and_annotaise_comparison.md` §2.2, §4.2 item 2).
   The SDG scheme has 17 labels. The first real multi-label run should be
   expected to over-code, and the DATALUTA pilot found the opposite bias in
   the *gold* (human false negatives, `decifra-dataluta-pilot/README.md`),
   so `set_size_ratio > 1` will be a mixture of model over-coding and gold
   under-coding that only the disagreement review can separate. Mitigations
   in this spec: the §8.2 signals on the Validation screen, `max_labels` as a
   hard lever, `per_variable` as default, per-label `boundary_notes`
   (Type III definitions) as the codebook-side control. Not mitigated here:
   the few-shot-worsens-it finding (§4.2 item 3 of the SBES doc), which
   needs its own experiment.
2. **The 2026-09-02 cache sketch is incomplete against the live code.** It
   omits `RunRecord.provider_mode == run.provider_mode` and
   `ExtractionRecord.original_result_json == ""` (`extraction.py:174-175`).
   Dropping the second would serve a human-edited row as if it were the
   model's answer. §4.3 restores both.
3. **The 2026-09-02 `ExtractionRecord` listing is stale.** It omits
   `evidence_verified`, `evidence_match_tier` and `original_result_json`
   (`db.py:119-124`), all live and all read by the frontend
   (`api.ts:166-170`). An implementer copying the listing would drop them.
4. **`estimate.py` did not exist when the earlier spec was written** (added
   2026-09-07). It calls `book.schema` and `book.build_messages(doc.text)`
   (`estimate.py:21-22`), both of which raise for a multi-variable codebook
   under the 2026-09-02 design, so `POST /runs/estimate` — and therefore
   the Run screen's cost preview — would 500 on the first multi-variable
   codebook. Step 3 covers it.
5. **Two frontend files read `spec.categories` directly** and will throw on
   a `variables:` spec: `CodebookEditor.tsx:61` and `RunsPage.tsx:96`. The
   earlier spec's frontend section does not mention the API normalization
   that avoids this (§9, second bullet).
6. **The TODO item's suggested shape under-specifies three things.**
   "`categoria` → `list[Literal[...]]`" gives the set no per-label evidence
   (§3.3) and no representation for a reviewed empty set in gold (§7.2);
   "the DB storing a JSON array" is right for the label set but, stored on
   `HumanLabelRecord` as one row per label, would be misread by the
   multi-coder rule at `app.py:439-443` (§5.3); and "validation branches on
   the codebook's declaration" is necessary but not sufficient —
   `agreement_report()` cannot be branched, it needs a sibling (§8.2).
7. **Delimiter and locale.** `;` as a set delimiter would round-trip badly
   through pt-BR Excel (§7.2). This is a real failure mode for this
   project's actual users, not a hypothetical.
8. **Raw-text codebook hashing** (`extraction.py:138`, `estimate.py:12`,
   `app.py:556`) means re-saving a codebook from the editor without changing
   its meaning invalidates joint-mode cache and fails the reproducibility
   "same codebook" check. §4.3 hashes the normalized spec instead; legacy
   rows keep their raw-text hash and are handled by §5.4.
9. **Evidence verification compounds.** The pilot saw 4-11% non-verbatim
   quotes per document with one quote each; with ~2.5 quotes per multi-label
   row the share of rows with at least one unverified quote rises
   accordingly. `evidence_verified` on a multi-label row is `all(...)`, so
   the row-level pill will be red more often; the per-selection tiers in the
   audit panel show which quote failed. This is the signal working, not a
   regression, but the UI copy should say so.
10. **Degenerate metric cases.** J(∅, ∅) = 1 by convention; a label that
    never appears in either pred or gold gets `kappa: null` and zeros;
    `set_size_ratio` is `null` when `mean_gold_set_size == 0`. All three are
    tests in step 4, not comments.
11. **Output-token estimate.** `settings.output_tokens_per_document`
    (`estimate.py:23`) is a flat per-document guess; for a multi-label
    variable the true cost scales with set size. Step 3 multiplies by
    `max_labels or len(categories)` as an upper bound and says so in the
    `method` string — an over-estimate is the right direction for a cost
    preview.
12. **The V7 hold.** The 2026-09-02 spec gates implementation on session
    `cifra-text-as-data-29`'s all-clear. The evidence that the experiments
    concluded is the 2026-09-07 merge `bf32d72` and the write-up
    `docs/research/2026-09-03_v7_pipeline_tuning_experiments.md`; no commit
    has touched `pilot_v7.py` since `123ec1a` (2026-09-02). This spec treats
    the hold as lifted pending the author's one-word confirmation (step 0).
13. **Name collision surface grows.** Export columns are now named after
    variables (§6), so the reserved set and the pairwise-distinctness rule in
    §2.3 are load-bearing, not cosmetic; a missing check surfaces as a
    silently overwritten CSV column, which is the worst kind of data bug for
    this tool's users.

*first* `.` after the `gold_` prefix. Variable names cannot contain `.`

to this pattern.
