## Design questions from the brief, answered

### 1. YAML shape

Add an optional `variables:` list. Each entry has `name`, `description`,
and `categories` (identical shape to today's category list — `label`,
`definition`, `positive_examples`, `negative_examples`, `boundary_notes`).
Today's single-variable shape (`categories:` directly under the top level)
stays valid as shorthand and is normalized internally to a single variable
named **`"main"`** — changed from `"category"` in revision 1 after round 1
review (both reviewers independently flagged the same problem): pairing
the variable name `"category"` with the output field also named `category`
produces nonsensical, redundant identifiers downstream — an exported CSV
column `category_category`, a validation report key
`per_variable.category.per_category`, and a real (if narrow) collision
risk if a multi-variable author explicitly names one of their own
variables `"category"`. `"main"` has none of these problems and reads
naturally ("the main/only variable of a single-variable codebook").

```yaml
# Today's shape, still valid, unchanged:
concept: protest
description: A collective public event expressing a political or social claim.
categories:
  - label: protest
    definition: ...
  - label: not_protest
    definition: ...

# New multi-variable shape:
concept: protest_coverage
description: >
  Whether a news article describes a protest, and if so, how the article
  frames the police response.
prompt_strategy: per_variable   # optional, default shown; see §4
variables:
  - name: is_protest
    description: Whether this document describes a protest event.
    categories:
      - label: protest
        definition: ...
      - label: not_protest
        definition: ...
  - name: police_framing
    description: How the article frames the police response, if any.
    categories:
      - label: supportive
        definition: ...
      - label: critical
        definition: ...
      - label: neutral_or_absent
        definition: ...
```

`validate_spec` rejects a spec that supplies **both** top-level
`categories` and `variables` (ambiguous — which one is authoritative).
Within `variables:`, each `name` must match `^[a-zA-Z_][a-zA-Z0-9_]*$`
(a valid Python/snake_case identifier — **new in this revision**, round 1
finding: Flash finding 7) — this is stricter than "any non-empty string"
because a variable name flows unescaped into a Pydantic field name (for
`joint` mode's nested schema, §4), a CSV/XLSX column-name component
(`category_<name>`), and a `?variable=` query parameter. Names must be
unique across the list, and none may collide with a fixed reserved set:
`{"main", "category", "rationale", "evidence_span", "id", "document_id",
"run_id", "variable"}` (also new in this revision, same finding) — this
blocks a user from naming a variable `"category"` (the exact ambiguity
`"main"` was chosen to avoid at the *default* level; explicit user choice
must be blocked too, not just discouraged) or `"id"`/`"document_id"`
(collides with existing row/export columns). Each variable's own
`categories` list is validated with the exact same per-category logic
already in `validate_spec` today (refactored into a helper so it isn't
duplicated). Category labels only need to be unique *within* their own
variable, not across variables.

### 2. Output field names

`category`, `rationale`, `evidence_span` — replacing `categoria`,
`justificativa`, `trecho_evidencia` everywhere. These are the exact names
`AGENTS.md`'s codebook-format section already uses to describe the
intended output ("a free-text `rationale` field and an `evidence_span`
field"), so this spec is bringing the implementation in line with the
project's own documented design, not inventing new names.

### 3. Row shape: one row per (document, variable)

`extractions` stays a narrow table: one `ExtractionRecord` row per
(document, variable), not one row per document with a JSON blob. Reasons:

- Every existing per-row operation (`PUT .../results/{id}` inline edit,
  the cache lookup, the error-row-on-failure path, the audit-trail
  `prompt_sent`/`raw_response` pair) already assumes "one row = one
  category decision with its own exact prompt and response." A JSON
  column would force every one of those to parse/rewrite a blob instead
  of touching one field, and would make `prompt_sent`/`raw_response` per
  *variable* impossible to represent cleanly.
- Filtering ("show me all `police_framing=critical` rows") and the
  validation report ("per-variable accuracy") are both plain `WHERE`
  clauses on a narrow table; both would need JSON-path queries or an
  application-side unpack on a wide table.
- `HumanLabelRecord` (gold labels) already works this way (one row per
  document, gaining `variable` too — see §5) — keeping predicted and
  gold rows structurally parallel keeps `agreement_report()`'s merge
  logic simple.

Cost: a run against an N-variable codebook writes N× the row count it
does today for the same corpus. This is judged acceptable — it's the same
row-count growth the LLM-call-count growth already implies (§4), and
pagination (not in scope for R1.1; `R5.2` in the roadmap) is the real
long-term answer to row count, not a schema choice here.

**Round 1 finding, fixed here (Flash finding 9)**: `list_runs`/`get_run`
today compute `total = len(documents)` and `processed = len(extractions)`
— on an N-variable run this shows `300 / 100` (300%) progress for 100
documents × 3 variables. Fixed: `total = len(documents) * len(codebook's
variables)`, so `processed`/`total` stays a meaningful fraction regardless
of variable count. `disclosure.py`'s equivalent prose ("`N` of `M`
documents have a persisted prompt_sent") is corrected the same way —
report extraction-row coverage against the true expected row count
(`documents × variables`, or `documents` for `joint` mode where one call
produces all variables — see §4), not against raw document count.

### 4. Prompt strategy: configurable per codebook, default one call per variable

**Revised after author feedback (2026-09-02): this is a configurable
per-codebook choice, not a single hardcoded strategy.** The YAML gains an
optional top-level field:

```yaml
prompt_strategy: per_variable   # default; or "joint"
```

`validate_spec` rejects any value other than `"per_variable"`/`"joint"`.
Both modes are real, tested code paths — not one built with the other
stubbed out — because the two serve genuinely different codebooks: a
two-variable codebook where both questions are cheap and independent
benefits from `per_variable`'s precise caching; a five-variable codebook
against long documents, where resending the full text five times is the
dominant cost, benefits from `joint`.

**`per_variable`** (default) — one LLM call per variable, chosen as the
default for three reasons:

1. **Audit trail stays exact.** One call → one variable's `prompt_sent`/
   `raw_response`, unambiguous.
2. **Cache invalidation stays precise.** Editing one variable's
   `categories` must not force every other variable's already-good,
   already-cached extractions to be thrown away and re-billed.
3. **Retry stays cheap and precise.** A failure on one variable for one
   document retries only that one call, not every variable for that
   document.

Real cost: N variables means N LLM calls per document, and the full
document text is resent in each call's prompt.

**`joint`** — one LLM call per document, returning every variable's answer
at once. Chosen by a codebook author who has judged that call-volume cost
matters more than per-variable cache precision. Concretely:

- `Codebook._from_spec` builds **one** combined Pydantic schema (nested:
  one sub-model per variable, each with its own `category`/`rationale`/
  `evidence_span`), and **one** combined instructions block (today's
  per-variable instructions, concatenated with a clear `## <variable
  name>` heading each).
- `run_extraction` makes **one** provider call per document instead of
  looping over variables, then unwraps the single nested result into N
  `ExtractionRecord` rows (one per variable). All N rows for that document
  share the same `prompt_sent`/`raw_response` — disclosed, not hidden: the
  disclosure report for a `joint`-mode run states explicitly that a row's
  audit trail covers the whole document's call, not that variable alone.
- **Cache key reverts to `(document, codebook_yaml_hash, model)`** — the
  whole-codebook hash. Editing any one variable's definition re-bills
  every variable for every document. This must be stated plainly in the
  YAML comment and any UI exposing this choice.
- A single document's provider-call failure in `joint` mode fails **all**
  of that document's variables together (one error row per variable, same
  error message).

**Round 1 finding, fixed here (Pro finding 1, independently corroborated
by Flash finding 5 — the single highest-confidence finding of this round,
since both reviewers caught it without prompting each other): the cache
lookup in `joint` mode cannot use `.first()`.** Revision 1's `extraction.py`
sketch inherited pre-R1.1's `session.exec(...).first()` cache-lookup
pattern unchanged. Pre-R1.1, a document has at most one cached row, so
`.first()` is correct. Under `joint` mode, a single cached document
produces **N** `ExtractionRecord` rows (one per variable, all sharing one
`codebook_yaml_hash`). Using `.first()` on a cache hit would silently
return only one variable's cached row and treat the run as fully served
from cache — **silently dropping N-1 variables' worth of data for every
cached document**, not erroring. Fixed in the `extraction.py` design
section below: `joint` mode's cache lookup uses `.all()` and explicitly
verifies all declared variable names are present among the cached rows
before accepting the hit; any missing variable invalidates the whole
document's cache (falls through to a fresh call), it does not partially
reuse what's there.

**Round 1 finding, fixed here (Flash finding 4 — a self-consistency bug in
revision 1's own code listing)**: revision 1's `Codebook._from_spec` code
snippet built `variables` but never read or passed `prompt_strategy`,
`joint_schema`, or `joint_instructions` into the constructed `Codebook`,
and `build_messages` had no path for joint mode at all — an implementer
following revision 1 literally would get a `joint` YAML setting that was
silently ignored, with the codebook always running as if it were
`per_variable`. Fixed in the `codebook.py` design section below with a
corrected code listing.

### 5. Gold-label CSV: one `gold_<variable>` column per variable

`gold_is_protest`, `gold_police_framing`, etc. — one column per declared
variable name, each independently optional per row (blank = "not yet
reviewed for this variable"). `upload_gold_labels` iterates the
codebook's variable names to know which columns to look for, and writes
one `HumanLabelRecord` per (document, variable, non-blank value) — same
all-or-nothing validity rule as today.

**Round 1 finding, fixed here (Flash finding 1 — data loss, the single
most severe finding of this round)**: today's replace-before-insert
delete query (both the manual-CSV path in `upload_gold_labels` and the
QualiLab-import path via `qualilab_doc_values_to_human_labels`) filters
on `codebook_id`/`source`/`document_id` but **not** on `variable`.
Verified directly against `upload_gold_labels`'s real delete query
(`app.py`) — it has no `variable` clause today, which is harmless
pre-R1.1 (there's only one variable, so the omission is a no-op), but
becomes a real bug the instant `variable` exists: re-uploading (or
correcting) gold labels for variable B would delete **every** existing
`HumanLabelRecord` for those documents, including variable A's
already-imported labels, which are not in the new upload at all. Fixed:
both delete queries gain `HumanLabelRecord.variable == variable`, scoping
the replace-on-reupload behavior to the one variable actually being
(re)imported.

**Round 1 finding, fixed here (Flash finding 2 — QualiLab export
unconditionally crashes on a multi-variable run)**: `POST
/runs/{run_id}/export-qualilab` today loads *all* of a run's
`ExtractionRecord` rows and hands them to
`inject_extractions_into_qualilab` unfiltered. On a multi-variable run,
that function would attempt to map every variable's category values
through a `reverse_value_mapping` built for one target variable/category,
and any other variable's category value would fail to resolve, aborting
the whole export with the existing "not a declared option" error. Fixed:
both `POST /corpora/{corpus_id}/import-qualilab-labels` and `POST
/runs/{run_id}/export-qualilab` gain a required `variable: str =
Form(...)`, and `app.py` filters `extractions = [e for e in extractions
if e.variable == variable]` before calling into `qualilab_interop.py`
(which itself needs its `categoria`/`category` references updated for §2
regardless).

### 6. Validation report keyed by variable

`GET /runs/{run_id}/validation` returns `{"per_variable": {"is_protest":
{...}, "police_framing": {...}}}` where each value is the same shape
`get_run_validation` returns today (`coverage`, `per_category`,
`disagreements`).

**Round 1 finding, fixed here (Flash finding 3 — the claim "`validation.py`
needs zero changes" was true but the *caller* design built on top of it in
revision 1 was not, and would crash): a single wide pivot across all
variables is the wrong shape.** §5 deliberately allows independent,
partial gold coverage per variable (a document can have
`gold_is_protest` filled and `gold_police_framing` blank). Pivoting both
predicted and gold rows into one wide DataFrame (one row per document, one
column per variable) necessarily introduces `NaN` for a variable with no
gold value yet on that document. `agreement_report()`'s `labels =
sorted(set(merged[gold_col]) | set(merged[pred_col]))` (validation.py)
then attempts to sort a set mixing `str` and `float('nan')`, which raises
`TypeError: '<' not supported between instances of 'float' and 'str'` in
Python 3 — not a hypothetical, a guaranteed crash the first time any real
codebook has uneven per-variable gold coverage, which §5 explicitly
designed for as the normal case.

**Corrected design**: `get_run_validation` does **not** build one wide
DataFrame. It loops over `codebook.variables` and, for each variable
independently: filters `extractions`/`human_labels` to that
`variable`, drops documents with no gold value *for that variable*
(exactly today's single-variable logic, just scoped per variable instead
of globally), and calls the existing, unmodified
`agreement_report(predicted_df, gold_df, id_col="id",
columns=["category"])` once per variable — narrow, single-column,
`NaN`-free by construction, because rows with no gold value for this
variable were already excluded before the call. The `{"per_variable":
{...}}` wrapper is assembled from N such independent, always-safe calls.
`validation.py` itself still needs zero code changes (that part of the
original claim holds) — the fix is entirely in how `app.py` calls it.

The same fix applies to `GET /runs/{run_id}/reproducibility` — round 1
review also caught (Flash finding 3, part 3) that feeding a multi-variable
extraction list directly into `reproducibility_report()` produces
duplicate `document_id`s (one row per variable per document) in what that
function expects to be a document-keyed comparison, raising
`agreement_report`'s existing "gold has more than one row for the same
id" guard. Fixed the same way: `get_run_reproducibility` loops per
variable and calls `reproducibility_report()` once per variable, narrow.

## Data model changes (`src/text_as_data/db.py`)

```python
class ExtractionRecord(SQLModel, table=True):
    __tablename__ = "extractions"

    id: int | None = Field(default=None, primary_key=True)
    run_id: int = Field(foreign_key="runs.id")
    document_id: int = Field(foreign_key="documents.id")
    variable: str = "main"              # NEW — the codebook variable this
                                         # row answers. "main" is the
                                         # normalized name for a legacy
                                         # single-variable codebook (§1).
    variable_spec_hash: str = ""        # NEW — see §4/extraction.py.
                                         # Empty for rows produced in
                                         # `joint` mode (§4).
    category: str                       # RENAMED from categoria
    rationale: str                      # RENAMED from justificativa
    evidence_span: str                  # RENAMED from trecho_evidencia
    tokens_used: int | None = None
    prompt_sent: str = ""
    raw_response: str = ""


class HumanLabelRecord(SQLModel, table=True):
    __tablename__ = "human_labels"

    id: int | None = Field(default=None, primary_key=True)
    document_id: int = Field(foreign_key="documents.id")
    codebook_id: int = Field(foreign_key="codebooks.id")
    variable: str = "main"              # NEW — same normalization as above
    category: str                       # unchanged name, already neutral
    coder: str
    source: str = "manual"
    layer: str = "final"
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
```

`variable` and `variable_spec_hash` are additive — `_ensure_columns`
already handles "add a column with a scalar default to an existing table"
automatically.

**The three renames (`categoria`→`category`, `justificativa`→`rationale`,
`trecho_evidencia`→`evidence_span`) are not additive** — `_ensure_columns`
explicitly never renames a column, by design.

**Round 1 finding, fixed here (Flash finding 6, independently
corroborated by Pro finding 2 — the second highest-confidence finding of
this round): a standalone one-shot migration script races against
`_ensure_columns()`.** Revision 1 proposed a separate
`scripts/migrate_r1_1_field_names.py`, run manually before first use.
Both reviewers independently identified the same failure sequence: if the
app, the frontend dev server, or the test suite starts even once against
a pre-R1.1 `codifica.sqlite` **before** that script is run,
`get_engine()`'s automatic `_ensure_columns()` call sees `category`,
`rationale`, `evidence_span`, `variable`, and `variable_spec_hash` as
"missing" and additively creates them as **empty** columns (its designed
behavior, correct for genuinely new columns, wrong here because these
three are renames, not new data). The old data stays stranded in
`categoria`/`justificativa`/`trecho_evidencia`. Running the migration
script afterward then fails outright (`duplicate column name`), leaving
the database permanently half-migrated with no automatic recovery path.

**Corrected design, adopting Pro's fix (structurally superior — it
removes the race condition instead of racing more carefully against it)**:
the rename logic moves *into* `_ensure_columns()` itself, run
automatically on every engine startup, **before** the existing
additive-column loop:

```python
_LEGACY_RENAMES = {
    "extractions": [("categoria", "category"), ("justificativa", "rationale"),
                     ("trecho_evidencia", "evidence_span")],
}

def _apply_legacy_renames(dbapi_connection) -> None:
    for table_name, renames in _LEGACY_RENAMES.items():
        existing = {row[1] for row in dbapi_connection.execute(
            f'PRAGMA table_info("{table_name}")'
        ).fetchall()}
        if not existing:
            continue  # table doesn't exist yet -- nothing to rename
        for old_name, new_name in renames:
            if old_name in existing and new_name not in existing:
                dbapi_connection.execute(
                    f'ALTER TABLE "{table_name}" RENAME COLUMN "{old_name}" TO "{new_name}"'
                )
```

Called from `get_engine()` immediately before `_ensure_columns()`. This
makes the rename unconditional and automatic — there is no longer a
"before you start the app, remember to run this script" step to forget,
and no ordering for `_ensure_columns()` to race against, because the
rename always runs first, every time, and is a no-op once the columns are
already renamed (the `new_name not in existing` guard). A brand-new
`codifica.sqlite` never has `categoria` to begin with, so
`_apply_legacy_renames` is a no-op for it too — `create_all()` creates the
renamed columns directly. (SQLite's `ALTER TABLE ... RENAME COLUMN` has
been supported since SQLite 3.25.0 (2018); the Python versions this
project targets all bundle a newer `sqlite3` than that.)

## `src/text_as_data/codebook.py` changes

**Round 1 finding, fixed here (Pro finding 3 — verified against real
`origin/main`, see Context): the pre-R1.1 `Codebook.build_messages`
signature already gained `include_persona: bool = True` (commit
`8c22f3c`, live, for `cifra-text-as-data-29`'s in-progress persona-
ablation experiments). Revision 1's proposed backward-compatible
signature dropped it, which would have broken that session's several-hour
runs the moment this code landed — directly contradicting this spec's own
stated goal of not disrupting them. Fixed below: `include_persona` is
preserved and threaded through.**

**Round 1 finding, fixed here (Flash finding 11): revision 1 removed
`Codebook.schema`/`Codebook.instructions` outright ("removed, not
deprecated-and-kept"). Any other in-progress or external code still
calling `codebook.schema` directly on a single-variable codebook (not
just `pilot_v7.py`'s scripts, which use `build_messages`, but anything
built against today's public `Codebook` attributes) would break with an
`AttributeError`. Fixed below: kept as read-only properties, valid only
for a single-variable codebook, since that's the only case where "the
codebook's schema" is unambiguous.**

```python
@dataclass
class CodebookVariable:
    name: str
    schema: type[BaseModel]      # {category: Literal[...], rationale: str, evidence_span: str}
    instructions: str
    examples: list[dict] = field(default_factory=list)

    def build_messages(self, text: str, include_persona: bool = True) -> list[dict]:
        ...  # exactly today's Codebook.build_messages body, unchanged


@dataclass
class Codebook:
    concept: str
    description: str
    variables: dict[str, CodebookVariable]   # insertion-ordered; >=1 entry
    prompt_strategy: Literal["per_variable", "joint"] = "per_variable"  # §4
    joint_schema: type[BaseModel] | None = None      # set only when
    joint_instructions: str | None = None            # prompt_strategy == "joint"

    def build_messages(
        self, text: str, variable: str | None = None, include_persona: bool = True
    ) -> list[dict]:
        """Backward-compatible with the pre-R1.1 signature (including the
        already-live `include_persona` parameter, §Context). `variable=None`
        requires exactly one entry in `self.variables` and uses it — this is
        what keeps `codebook.build_messages(text)` and
        `codebook.build_messages(text, include_persona=False)` (both real,
        live call shapes today) working unchanged for single-variable
        codebooks specifically, which is the only case any current caller
        uses."""
        if self.prompt_strategy == "joint":
            if variable is not None:
                raise ValueError("variable= is not meaningful when prompt_strategy is 'joint'")
            return self._build_joint_messages(text, include_persona)
        if variable is None:
            if len(self.variables) != 1:
                raise ValueError(
                    "build_messages() needs an explicit variable= for a "
                    "multi-variable codebook"
                )
            variable = next(iter(self.variables))
        return self.variables[variable].build_messages(text, include_persona)

    def _build_joint_messages(self, text: str, include_persona: bool) -> list[dict]:
        ...  # uses self.joint_instructions instead of a per-variable
             # CodebookVariable's own instructions; same persona-prefix
             # handling as CodebookVariable.build_messages

    @property
    def schema(self) -> type[BaseModel]:
        """Kept for backward compatibility with any code (including
        `cifra-text-as-data-29`'s in-progress scripts) still reading
        `codebook.schema` directly. Valid only for a single-variable
        codebook, since a multi-variable one has no single schema to
        return — matches how `build_messages(text)` already requires an
        explicit `variable=` in that case."""
        if len(self.variables) != 1:
            raise AttributeError(
                "multi-variable codebook has no single .schema; use "
                "codebook.variables[name].schema"
            )
        return next(iter(self.variables.values())).schema

    @property
    def instructions(self) -> str:
        if len(self.variables) != 1:
            raise AttributeError(
                "multi-variable codebook has no single .instructions; use "
                "codebook.variables[name].instructions"
            )
        return next(iter(self.variables.values())).instructions

    @classmethod
    def _from_spec(cls, spec: dict) -> "Codebook":
        validate_spec(spec)
        variable_specs = _normalize_variables(spec)   # §1's shorthand expansion
        variables = {
            vs["name"]: _codebook_variable_from_spec(vs) for vs in variable_specs
        }
        prompt_strategy = spec.get("prompt_strategy", "per_variable")
        joint_schema = None
        joint_instructions = None
        if prompt_strategy == "joint":
            joint_schema, joint_instructions = _build_joint_schema_and_instructions(variables)
        return cls(
            concept=spec["concept"],
            description=spec["description"],
            variables=variables,
            prompt_strategy=prompt_strategy,
            joint_schema=joint_schema,
            joint_instructions=joint_instructions,
        )
```

`_codebook_variable_from_spec` is today's `_from_spec` body (schema
`create_model` + instructions-string building), factored out unchanged
except for the three field renames and operating on one variable's
`categories` instead of the whole spec's. `_build_joint_schema_and_
instructions` is new: builds one nested `create_model` (one sub-model
field per variable name, using each `CodebookVariable.schema`) and
concatenates each variable's instructions block under a `## <name>`
heading, per §4.

## `src/text_as_data/extraction.py` changes

`extract()` (the low-level `pandas`-in/out helper) gains `variable: str |
None = None` and `include_persona: bool = True` parameters, threaded
straight through to `codebook.build_messages(row[text_col], variable,
include_persona)` — same backward-compatible defaults as above.

`run_extraction()` branches on `codebook.prompt_strategy`:

```python
if codebook.prompt_strategy == "per_variable":
    for document in documents:
        for variable_name, variable in codebook.variables.items():
            variable_hash = hashlib.sha256(
                json.dumps(_variable_spec_slice(spec, variable_name), sort_keys=True).encode()
            ).hexdigest()
            cached = None
            if not run.bypass_cache:
                cached = session.exec(
                    select(ExtractionRecord).where(
                        ExtractionRecord.document_id == document.id,
                        ExtractionRecord.variable == variable_name,
                        ExtractionRecord.variable_spec_hash == variable_hash,
                        # NOT joined on RunRecord.codebook_yaml_hash here --
                        # that would re-couple this to the whole codebook's
                        # hash and defeat the whole point of a per-variable
                        # hash (editing variable B would then invalidate
                        # variable A's cache again). RunRecord.model is
                        # still checked via a join, since a cache hit must
                        # still match the model that produced it.
                    )
                    .join(RunRecord, ExtractionRecord.run_id == RunRecord.id)
                    .where(RunRecord.model == run.model, ExtractionRecord.category != ERROR_CATEGORIA)
                    .order_by(ExtractionRecord.id.desc())
                ).first()   # correct here: at most one cached row per (doc, variable, hash, model)
            ...  # one provider call on miss, one ExtractionRecord row either way
else:  # "joint"
    for document in documents:
        cached_rows = []
        if not run.bypass_cache:
            cached_rows = session.exec(
                select(ExtractionRecord)
                .join(RunRecord, ExtractionRecord.run_id == RunRecord.id)
                .where(
                    ExtractionRecord.document_id == document.id,
                    RunRecord.codebook_id == run.codebook_id,
                    RunRecord.codebook_yaml_hash == codebook_yaml_hash,
                    RunRecord.model == run.model,
                    ExtractionRecord.category != ERROR_CATEGORIA,
                )
            ).all()   # MUST be .all(), not .first() -- a joint-mode document
                       # has N cached rows, one per variable (§4, round-1
                       # finding: Pro finding 1 / Flash finding 5). Using
                       # .first() here would silently serve only one
                       # variable's cached row and treat the whole document
                       # as cache-complete, dropping the other N-1 variables.
        cached_variable_names = {row.variable for row in cached_rows}
        if cached_rows and cached_variable_names >= set(codebook.variables):
            ...  # full cache hit: reuse all N cached rows as-is
        else:
            ...  # cache miss (partial or none): one provider call using
                 # codebook.joint_schema/joint_instructions, unwrapped into
                 # one ExtractionRecord row per variable, all sharing this
                 # one call's prompt_sent/raw_response, variable_spec_hash=""
```

In `per_variable` mode, a single document's single-variable failure still
only produces one `__error__` row for that (document, variable) pair. In
`joint` mode, one failed call produces an `__error__` row for every
variable of that document at once (§4).

## `src/text_as_data/app.py` changes

- `GET /runs` / `GET /runs/{run_id}` — `total` is
  `len(documents) * len(codebook.variables)` (`len(documents)` for
  `joint` mode, where one call covers every variable), not raw document
  count (§3, round 1 fix).
- `GET /runs/{run_id}/results` — rows now include `variable`. Add an
  optional `?variable=` query filter. No other shape change; the frontend
  groups by document client-side (see Frontend, below).
- `PUT /runs/{run_id}/results/{extraction_id}` — request body renamed
  `{category, rationale}`; validates `category` against *that row's own
  `variable`*'s category labels (look up the matching `CodebookVariable`
  by `extraction.variable`, not the whole codebook's).
- `POST /runs/{run_id}/gold-labels` — reads one `gold_<variable>` column
  per declared variable (§5); the replace-before-insert delete query is
  scoped to `HumanLabelRecord.variable == variable` per document/variable
  pair being (re)imported (§5, round-1 fix — was previously unscoped and
  would have deleted other variables' gold labels).
- `GET /runs/{run_id}/validation` and `GET /runs/{run_id}/reproducibility`
  — both loop per variable and call the existing `agreement_report()` /
  `reproducibility_report()` once per variable on narrow, gold-filtered
  data (§6, round-1 fix — a single wide pivot with `NaN` gaps was
  revision 1's design and crashes on real partial-coverage data).
- `GET /runs/{run_id}/export` — CSV/XLSX export pivots to one row per
  document with per-variable column groups
  (`category_is_protest, rationale_is_protest, evidence_span_is_protest,
  category_police_framing, ...`) **only when the codebook has more than
  one variable**. For a single-variable (`"main"`) codebook, export keeps
  today's flat, unsuffixed column names (`category`, `rationale`,
  `evidence_span`) unchanged — this both avoids the `category_main`
  redundancy the `"main"` default would otherwise still produce in
  exports, and is a real backward-compatibility win: an existing
  single-variable gold-label CSV/export shape is untouched by this whole
  migration. The pivot itself is built as a `list[dict]` inside `app.py`
  before calling `export.py`'s existing, unmodified writers — `export.py`
  needs no changes; it was never told to build the pivoted shape itself,
  which round 1 review (Flash finding 10) correctly pointed out revision
  1 left unstated. JSON export nests: one object per document with a
  `variables: {is_protest: {...}, police_framing: {...}}` map (also only
  for multi-variable codebooks; single-variable JSON export stays flat).
- `POST /runs/{run_id}/export-qualilab` and `POST
  /corpora/{corpus_id}/import-qualilab-labels` — both gain a required
  `variable: str = Form(...)`. The export endpoint filters extractions to
  that variable before calling `inject_extractions_into_qualilab` (§5,
  round-1 fix — unfiltered, multi-variable extractions crash that
  function outright today).
- `POST /codebooks` / `PUT /codebooks/{id}` — the request model
  (`CodebookSpecRequest` today: `concept`, `description`,
  `categories: list[CategorySpec]`) gains `variables:
  list[VariableSpec] | None = None` and `prompt_strategy:
  Literal["per_variable", "joint"] = "per_variable"`, mirroring the YAML
  shape (§1). **Round 1 finding, fixed here (Flash finding 8)**: revision
  1 specified the YAML/engine side of this but never updated the actual
  REST request model — as written, `POST /codebooks` would 422 on any
  multi-variable submission regardless of what the engine itself supports.

## Frontend changes (design-level; exact layout is implementer's call)

- `frontend/src/api.ts` — `ExtractionResult` gains `variable: string`;
  `category`/`rationale`/`evidence_span` replace the Portuguese names;
  `updateExtraction` signature follows. `CodebookSpec` (or equivalent
  request type) gains `variables`/`prompt_strategy` mirroring the backend
  request model above (round 1 fix, Flash finding 8's frontend half).
- `frontend/src/CodebookEditor.tsx` — needs a repeatable "variable" block
  (name + description + the existing category-list sub-editor, reused
  once per variable) instead of one fixed category list, plus a
  `prompt_strategy` toggle with the §4 cost/cache tradeoff explained
  inline. This is the largest frontend change in this brief and deserves
  its own short design note before implementation (not fully specified
  here).
- `frontend/src/ResultsTable.tsx` — results are grouped by `document_id`
  client-side into one row per document with one column group per
  variable (mirroring the CSV export shape above; single-variable
  codebooks keep today's flat single-column layout unchanged), plus a
  variable selector alongside today's existing category filter.
  **Round 1 finding, fixed here (Pro finding 5)**: today's inline-edit
  state (`editingId` tracking one row) is row-based, which maps cleanly
  to one `extraction_id` in the current one-row-per-document-per-run
  shape. Once a table row represents a document with **multiple**
  extractions (one per variable), inline editing must become **cell-based**
  — `editingId`/edit state tracked per (document, variable) cell, each
  cell's "Edit" action targeting that cell's own specific `extraction_id`
  — not a single row-level edit state trying to cover every variable's
  column at once.
- `frontend/src/ValidationPanel.tsx` — one section per variable (e.g.
  tabs, or stacked panels), each rendering today's existing
  coverage/per-category/disagreements layout unchanged, fed by the
  corrected per-variable `GET /runs/{run_id}/validation` response (§6).

## Testing

- `codebook.py`: shorthand YAML still normalizes to
  `variables == {"main": ...}`; explicit `variables:` YAML with 2+
  entries validates and derives 2+ independent schemas; duplicate
  variable `name` rejected; both `categories` and `variables` present at
  once rejected; a variable named `"category"` (or any other reserved
  name) rejected; a variable name with a space, hyphen, or leading digit
  rejected (§1, round-1 fix); duplicate category labels *within* one
  variable rejected, but the same label allowed to repeat *across*
  variables.
- `build_messages(text)` and `build_messages(text, include_persona=False)`
  (no `variable=`) both still work for a single-variable codebook and
  raise `ValueError` for a multi-variable one — the backward-compatibility
  contract, tested explicitly since `cifra-text-as-data-29`'s live scripts
  depend on exactly this call shape not breaking (round-1 fix: Pro finding
  3). `codebook.schema`/`codebook.instructions` work for a single-variable
  codebook and raise `AttributeError` for a multi-variable one (round-1
  fix: Flash finding 11).
- `extraction.py`, `per_variable` mode: a 2-variable codebook run produces
  2 `ExtractionRecord` rows per document; editing only variable B's
  categories invalidates variable B's cache but not variable A's; one
  variable's provider failure produces an error row for only that
  variable.
- `extraction.py`, `joint` mode (round-1 addition, both new findings):
  a 2-variable `joint` codebook run makes exactly one provider call per
  document (assert call count) and produces 2 `ExtractionRecord` rows
  sharing identical `prompt_sent`/`raw_response`; a **partial** cache
  (one of two variables' rows present for a document, e.g. from a prior
  interrupted run) is treated as a cache **miss** and makes a fresh call
  rather than serving the incomplete set (the specific bug both
  reviewers caught); editing one variable's categories invalidates both
  variables' cache for that document; one failed call produces error rows
  for every variable of that document.
- `app.py`: results/validation/reproducibility/export/gold-labels
  round-trip for a 2-variable codebook end to end; validation/
  reproducibility specifically tested with **uneven** gold coverage
  (one variable labeled, the other not, for the same document) to
  confirm no `NaN`-sort crash (round-1 fix: Flash finding 3); `PUT
  .../results/{id}` rejects a `category` value valid for the *other*
  variable but not this row's own; gold-label re-upload for variable B
  does not delete variable A's existing gold labels (round-1 fix: Flash
  finding 1); QualiLab export against a multi-variable run succeeds when
  scoped to one `variable` and does not attempt to resolve other
  variables' values (round-1 fix: Flash finding 2); a single-variable
  codebook's CSV/JSON export is byte-for-byte the same flat shape as
  before this migration; `list_runs`/`get_run` progress fraction reflects
  `documents × variables`, not raw extraction count (round-1 fix: Flash
  finding 9).
- Startup rename: a fixture SQLite file with the old `categoria`/
  `justificativa`/`trecho_evidencia` columns, opened via `get_engine()`,
  ends up with the renamed columns and the old data intact, with no
  separate manual step (round-1 fix, replacing revision 1's standalone
  migration-script test: Flash finding 6 / Pro finding 2); calling
  `get_engine()` twice against the same already-migrated file is a no-op
  the second time.
- Full existing single-variable test suite still passes, with field names
  updated (`categoria`→`category` etc.) throughout — this is the
  brief's own stated acceptance bar for "nothing regressed."

## Explicit non-goals (this revision)

- Cross-variable consistency checks (e.g. "if `is_protest=false`, require
  `police_framing=neutral_or_absent`") — a codebook-authoring concern, not
  a pipeline one.
- Actually moving `pilot_v7.py` (§7) — location is decided, execution is
  deferred pending `cifra-text-as-data-29`'s in-progress experiments.
- Any UI-level design for `CodebookEditor.tsx`'s multi-variable authoring
  flow beyond the shape sketched above.
- Pagination of results/exports for very large corpora (`R5.2`).
- Switching an existing codebook's `prompt_strategy` after it already has
  cached extractions — both modes' cache keys are structured so that
  changing the field simply stops matching old rows (new rows accumulate
  under the new mode's key shape; old rows are neither deleted nor
  reinterpreted) rather than erroring, but no explicit UI/warning for this
  transition is designed here.
