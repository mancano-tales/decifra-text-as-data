# R1.1 Step 3 — Extraction, estimates and storage consume variables — Implementation Plan

> **Status:** Approved by the author in chat on 2026-09-27; implementation verified; PR #8 is open for author review and merge.
> **Issue:** [#6](https://github.com/mancano-tales/decifra-text-as-data/issues/6)
> **Spec:** `docs/superpowers/specs/2026-09-13-r1.1-multi-variable-and-multi-label-codebooks-design.md`, especially §§2–5.4, §10 step 3 and §15.

**Goal:** Make extraction, cost estimates and SQLite persistence consume the normalized `Codebook.variables` contract from step 2. A synthetic multi-variable codebook with single-label and multi-label variables must run through the existing API, with one extraction row per (document, variable), while existing single-variable codebooks remain compatible.

**Scope:** Implement §10 step 3 only. Use the default `prompt_strategy: per_variable`; `joint` remains deferred to step 8 and must continue to fail clearly. Do not implement the results/validation UI or other API response projections assigned to steps 5–7, the guarded legacy cache backfill assigned to step 10, or later step 11 documentation examples. The existing author sign-off in spec §15 governs all multi-label details.

**Architecture:** `Codebook` remains the source of each variable's schema, instructions, labels and stable `variable_spec_hash`. For every document-variable pair, extraction builds that variable's prompt/schema, checks cache using the variable hash plus all live safety filters, and stores one `ExtractionRecord`. Single-label output maps to `category`/flat rationale/evidence. Multi-label output maps to `selections_json` in codebook label order, with duplicate labels removed (first occurrence wins); `label_set()` exposes a common set view. Per-label evidence is verified per selection; per-set evidence is verified once and follows the §15 storage shape. SQLite migration is additive and relies on the existing `_ensure_columns()` mechanism.

## Risks and boundaries

- The schema supports both `per_label` and `per_set`; storage must keep `label_set()` independent of evidence granularity so downstream validation can consume either form.
- Variable hashes must be the cache identity, or editing one variable would invalidate unrelated work. Preserve the live cache guards documented in spec §4.3.
- Step 10's guarded backfill is deliberately separate. Additive migration will give pre-existing rows the legacy defaults, but their blank `variable_spec_hash` will not qualify as a new per-variable cache hit until that later step.
